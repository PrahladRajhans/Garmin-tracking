# Guide for AI assistants (Claude, ChatGPT, others)

You are looking at a personal Garmin analytics project. Read `HANDOVER.md` first (goal, references, what's left), then this file and `ARCHITECTURE.md`.

## Context
- **One user:** male, 29, 76.5 kg, Garmin Forerunner 955 (wrist HR only, no chest strap), Asia/Kolkata time zone. Right knee a little weak. No goal race: general fitness, maybe a marathon later. Max HR not tested (policy: 188 from data; see `METRICS.md`).
- **Goal:** match or beat paid connectors (Fitness AI Connector, AthleteData) and app insights (Whoop, Oura, Fitbit, Bevel, Garmin, Strava, Runalyze) for free, with every calculation transparent.
- **Single plan:** `ROADMAP.md`. History: `CHANGELOG.md`. Formulas: `METRICS.md`. Dashboard design: `DASHBOARD_PLAN.md`. Research: `research_notes/`.

## Rules for changes
1. After every change, add a `CHANGELOG.md` entry. Update `README.md` if tools, setup or config changed, and `METRICS.md` for any formula.
2. Run `pytest` and `ruff check .` before committing. CI must pass.
3. MCP SDK is 2.x: `from mcp.server.mcpserver import MCPServer` (not FastMCP).
4. Never commit credentials, API keys or token files.
5. Fix root causes, not symptoms. Sense-check new numbers against real data and Garmin's values, and watch units (FIT cadence is per foot ×2; HR zone upper bounds are exclusive; sleep < 3 h is an incomplete record).
6. Say when data is too thin. Prefer `available: false` with a reason over a number that looks precise.
7. Plain language on anything the user sees: "fitness", not CTL; "how sure", not r/CI.
8. Keep `ROADMAP.md` as the one plan. Mark dropped items with the reason, never silently delete them.
9. For a multi-step change, state the goal, priorities, dependencies and acceptance checks before editing implementation. Record what shipped and which verification still depends on the owner's environment.

## Reviewing the design
Want to suggest dashboard improvements? Start with `DASHBOARD_PLAN.md` §6–8 (UI map, design system, hosting), the screenshots in `docs/screenshots/`, and `src/garmin_mcp/dashboard.py`. The dashboard is one HTML file generated by Python. Keep UI controls offline in the bundled script. Enforce its exact hash in the document policy and keep the charts and linked sections readable when scripting is unavailable.

When narration scope, prompts, validation or Ollama support changes, update [docs/OLLAMA.md](docs/OLLAMA.md) alongside the changelog and metrics rules.

The owner explicitly rejects Chart readings dropdowns across all pages. Keep direct chart selection and accessible announcements. Do not reintroduce a separate list of plotted readings.

Every chart must answer a useful question with comparable evidence, interpretation and coverage. Avoid raw metric-versus-date plots that connect unrelated runs or long data gaps. Running form must account for pace, terrain and measurement availability. Prefer a clear supported comparison and next check when a plot adds no insight.

No dropdowns of raw data that duplicate a chart or displayed metric, regardless of their label. This includes split times, weekly totals, recorded efforts and all recorded values. Verify every page, including split charts, when changing disclosures.
